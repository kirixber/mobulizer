# Mobulizer UDP Protocol

Mobulizer uses two UDP ports:

| Port | Direction | Purpose |
|------|-----------|---------|
| `49321` | Windows → Android | Visualization frames |
| `49322` | Android → Windows | Client control messages |

## Visualization packet

Each visualization packet starts with the ASCII magic:

```text
CAVA
```

The binary header is:

```text
offset  size   type
0       4      ASCII "CAVA"
4       8      uint64 little-endian timestamp (microseconds)
12      2      uint16 little-endian bar count
14      ...    uint16 little-endian bar values
```

Each bar value is in the range:

```text
0 .. 65535
```

The Android client converts the value to a normalized floating-point value:

```text
value / 65535.0
```

## Example packet

For a packet containing 40 bars:

```text
4 bytes   magic
8 bytes   timestamp
2 bytes   bar count = 40
80 bytes  40 × uint16 bar values
```

Total:

```text
94 bytes
```

## Timestamp

The timestamp is generated by the Windows bridge using its monotonic clock.

The timestamp allows the Android client to reason about the logical time of a frame instead of relying only on when the UDP packet physically arrived.

## Control message

The Android client sends:

```text
BARS <width>
```

Example:

```text
BARS 1200
```

The Windows bridge converts the requested display width into an even number of bars using its configured bar-width target and limits the result to the supported range.

## Current bar range

The Windows client currently supports:

```text
minimum: 24 bars
maximum: 64 bars
```

## Delivery model

Visualization packets use UDP.

No delivery acknowledgement is required.

A missing frame is acceptable because the next frame will arrive shortly after it. The client should prefer a newer frame rather than waiting for retransmission of an older one.

## Important implementation rule

Visualization frames represent a stream, not a reliable message queue.

Do not build application logic that depends on receiving every individual frame.
